# ADR-002：四步工作台减负——服务端状态、统一决定、操作日志撤销

- 状态：已采纳（2026-11-26）
- 关联：PLAN_V1.4 §0.4、§3–§6；`docs/design/DESIGN.md`

## 背景
用户确认的 Direction D3 保留了四步工作台（产品资料 / 知乎认知洞察 / 海外内容 / 发布前检查）的布局和视觉，同时要求“复杂留给系统”：一键运行，用户只做 3 次真正的判断，每个操作都能撤销，编辑后自动复查。

## 决定
1. **服务端是唯一的状态源。** 每个项目的工作台状态（资料、事实、知乎建议、正文结构、检查问题、决定）以一个 JSON 文档存在 SQLite 表 `wb_projects` 中。前端只渲染 `GET /api/projects/{id}/workspace` 的结果，写操作都走 API，返回新的 workspace。
2. **正文是结构化的片段，不是 HTML。** 每段内容由多个条目组成，条目由片段组成：普通文本、决定占位（`slot`）、系统修订（`fix`，有原句和改后两个版本）、知乎建议控制的写法（`ins`）、设置控制的写法（`set`）。前端据此渲染绿色虚线、琥珀占位和红色标记；导出时由服务端拼成 Markdown，未决定的占位写成 `[待确认]`。
3. **用户手改过的条目改存纯文本覆盖（`text`），并标记 `user_edited`**，之后不会被重新生成、设置变更或建议切换覆盖。保存后服务端立即对这一段做规则复查，新出现的风险说法记为 `user_introduced` 问题，进入「需要你决定」。
4. **统一决定接口** `POST /api/projects/{id}/decisions/{decision_id}`，覆盖四类决定：批量确认事实、冲突取值（含自填）、计划功能写法、用户新写风险的“换 / 保留”。系统只写推荐（`recommended`），不替用户选定。
5. **操作日志 `wb_actions`**：每个写操作都记录操作前后的完整状态快照。`POST /api/projects/{id}/actions/undo` 按栈撤销最近一次操作。工作台状态很小（几十 KB），用全量快照比计算补丁更可靠。
6. **保守自动修订的守卫**：只允许 `remove_claim` / `soften_claim` / `terminology` / `unit_boundary` 四类；冲突和计划功能永远不自动处理。撤销 `severity=high` 的修订时必须带 `reason_code`。
7. **骨架阶段的生成方式**：PulseRing 示例资料包走确定性的演示流水线（`llm_mode=fake`，界面标注「开发占位 · 非真实运行」）；用户上传的其他资料走启发式的事实抽取和模板生成，同样如实标注。PR-03 到 PR-06 逐层替换为真实模型和知乎检索。

## 影响
- 撤销、复查、决定的语义集中在服务端，前端不需要维护复杂状态，也便于测试。
- 全量快照会随着项目变大而增长。正式版如果单个项目超过 1 MB，改为存补丁。
